# Hypothesis Builder — фаза 4

## Среда

`01-research/`. Результаты:
- `insights/hypotheses.md` — [`hypotheses.md`](../../../../../design/_shared/templates/hypotheses.md);
- `insights/assumptions.md` — [`assumptions.md`](../../../../../design/_shared/templates/assumptions.md).

Предусловие: `insights/jtbd.md`, `insights/pains.md`, `insights/opportunities.md`.

## Goal

Явно назвать, во что мы **верим**, но ещё не доказали. PRD строится на гипотезах,
которые можно опровергнуть — не на «мы точно знаем».

## Process

1. Пройди insights и brief. Выпиши всё, что звучит как утверждение без источника.
2. **Гипотезы** — формат Lean UX (Gothelf):

> Мы верим, что **[решение/изменение]** для **[сегмент]**
> приведёт к **[измеримый исход]**.
> Узнаем, когда увидим **[сигнал]**.

Типы: problem / solution / growth. Минимум 5, максимум 12.

3. **Допущения** — что должно быть правдой, чтобы продукт имел смысл.
   Сортируй по риску (desirability → feasibility → viability).
4. **Evaluator pass**: для каждой гипотезы проверь falsifiability:
   - есть ли конкретный сигнал проверки?
   - можно ли опровергнуть за 1–2 недели?
   Если нет — переформулируй.
5. Выбери топ-3 для первой проверки. Запиши в `NOTES.md`.
6. Обнови `outputs/research-digest.md` — таблица гипотез.

## Gate

Переход к `research-to-prd` только если:
- [ ] ≥5 гипотез в Lean-формате;
- [ ] у каждой — способ проверки;
- [ ] карта допущений с хотя бы одним high-risk пунктом;
- [ ] топ-3 приоритета названы.

## Rules

- Гипотеза ≠ факт. Факты остаются в insights с источниками.
- «Пользователям нужна наша фича» — плохая гипотеза. Лучше: «Мы верим, что
  автоматический отчёт для PM сэкономит 2ч/нед — узнаем по time-on-task в прототипе».
- Не писать UI-решения в problem-гипотезах.

## Frameworks

Lean UX (Gothelf), Assumptions mapping, RICE для приоритизации проверок (опционально).
