# Figma DS Link: привязка агента к дизайн-системе

Проблема, которую решает скилл: агент не хранит дизайн-систему в голове. Каждый запрос он «вспоминает» её заново: сканирует файл, тратит контекст и время, промахивается мимо компонентов и собирает отсебятину. Лечится это индексом: компактным описанием системы, которое живёт в среде и по которому агент находит нужное за один шаг.

Работа в два режима: НАСТРОЙКА (один раз) и СБОРКА (каждый день).

## Режим 1: Настройка (один раз)

Попроси у пользователя ссылку на Figma-файл дизайн-системы (нужен подключённый Figma MCP). Затем построй в папке проекта структуру `ds/`:

### 1. `ds/INDEX.md`: каталог компонентов

Пройди по страницам файла через метаданные (не тяни полные узлы) и собери таблицу всех компонентов:

```
| Компонент | Варианты | Назначение | Страница |
|---|---|---|---|
| Button | primary, secondary, ghost · 3 размера | Главное действие экрана | Components |
| ListRow | icon, avatar, chevron, switch | Строка списка, базовый блок экранов | Components |
```

Назначение пиши в одну строку своими словами, глядя на компонент: по нему ты потом будешь выбирать, что использовать. Большой файл индексируй порциями по страницам или секциям: не пытайся прочитать всё одним вызовом, у ответов есть лимиты.

### 2. `ds/tokens.md`: токены

Выгрузи переменные файла (цвета, отступы, радиусы) и текстовые стили в список «имя → значение → для чего». Если в проекте есть код с токенами (tokens.css, тема), сопоставь имена и пометь расхождения: дальше источником истины считаются переменные Figma.

### 3. `ds/playbook.md`: правила сборки

Зафиксируй правила, без которых сборка разваливается. Обязательный минимум:

- **ID не хранить.** ID узлов меняются при пересборке компонентов. В индексе живут имена; карту «имя → текущий узел» строй в начале сессии одним проходом по файлу и держи в памяти сессии, не в файлах.
- **Три закона размеров.** Каждый инстанс должен уметь отвечать на ширину и высоту: авто-лейаут или констрейнты; фиксированные размеры только у иконок и аватаров; текст внутри компонентов тянется, а не обрезается.
- **Значения только из токенов.** Цвета через переменные, текст через стили. Пиксельные значения на глаз запрещены: если нужного токена нет, спроси пользователя, а не изобретай.
- **Каркас экрана.** Опиши, из чего состоит типовой экран этой системы (шапка, контент, нижняя навигация, отступы рамки) и какого размера фрейм.
- **Грабли.** Сюда же дописывай всё, обо что споткнулся в этом файле: заглушки, битые инстансы, особые компоненты. Плейбук растёт от сессии к сессии.

### 4. Описания в самой Figma (по желанию, но сильно помогает)

Каждому компоненту в Figma допиши описание: одна строка назначения, и если есть код, последняя строка «Код: путь → Компонент()». Это видно любому в панели компонента и связывает слои без платных фич.

Закончив настройку, покажи пользователю сводку: сколько компонентов, токенов и стилей в индексе, что вызвало вопросы.

## Режим 2: Сборка (каждый день)

Когда просят собрать макет или экран по системе:

1. **Читай индекс, не файл.** Выбор компонентов делай по `ds/INDEX.md`. В Figma ходи точечно, только за узлами, которые реально используешь.
2. **Карта узлов в начале сессии.** Один проход: собери соответствие «имя компонента → текущий ID» для нужной страницы. Дальше работай по карте.
3. **План до сборки.** Перед сборкой экрана покажи пользователю текстом план композиции: какие компоненты, в каком порядке, что в данных. Собирай после подтверждения.
4. **Новые макеты в отдельном файле.** Не собирай в файл, где уже есть чужие коллекции переменных: дубликаты коллекций ломают привязку. Библиотека подключается к новому файлу, макеты живут там.
5. **Проверь себя.** После сборки сверь результат с правилами плейбука: токены, размеры, текст не обрезан. Найденные новые грабли допиши в `ds/playbook.md`.

## Поддержка индекса

Индекс это снимок, он стареет. Правила:

- Изменил или добавил компонент: сразу обнови его строку в `ds/INDEX.md`.
- Изменились переменные: перегенерируй `ds/tokens.md`.
- Раз в несколько сессий сверяй индекс с файлом: пройди по страницам метаданными и сравни список с таблицей. Расхождения показывай пользователю списком: что появилось, что пропало, что переименовано.

Если индекс и файл разошлись сильно, честно скажи, что нужна переиндексация, и не собирай макеты по устаревшим данным.
