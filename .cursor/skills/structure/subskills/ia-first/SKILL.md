# Сначала архитектура, потом экраны

## Философия

Красивые экраны, разложенные по табам, ещё не продукт. Пока не описан граф — какой интерактив куда ведёт и при каком условии — половина тапов окажется в никуда, а половина сущностей будет открываться из разных мест по-разному.

Типичная картина: экраны собраны и приняты по виду, а на первом же прогоне выясняется, что тап по карточке ничего не открывает, входящие уведомления ведут в пустоту, а два разных действия закрывают одну и ту же работу пользователя. Лечится порядком: сначала архитектура (что, зачем, куда, когда), потом карта экранов.

## Что делаешь

Пишешь `product/IA.md` (или аналог в своём проекте) — навигационную истину продукта. Экраны и код мапятся отсюда; **узла или перехода, которого нет в этом файле, не существует**.

### 1. Модель навигации

Опиши слои и способ выхода из каждого. Типовая мобильная модель:

| Слой | Роль | Вход | Выход |
|---|---|---|---|
| Корень | табы | таббар | переключение таба |
| Пуш | просмотр/редактирование сущности | тап по сущности | назад, ровно один шаг |
| Шит | короткий выбор или форма в контексте | действие на экране | свайп вниз / мимо / кнопка |
| Оверлей | момент-праздник | событие | явное действие |

Плюс правила: где виден таббар, может ли пуш открываться из пуша, что делает системная кнопка «назад».

### 2. Таблица узлов

На каждый узел — четыре колонки: **что это · зачем · когда появляется · куда ведёт каждый интерактив**. Переходы пишутся с условиями:

```
♥ → лайк-шит [есть свои идеи] / сразу лайк [идей нет]
✕ → следующая карточка
тап по инфо → профиль человека
```

Условие — часть архитектуры: «шит появляется только если есть идеи» — это решение, а не деталь реализации.

### 3. Граф

Mermaid-схема основных рёбер: видно циклы, тупики и узлы-сироты. Всё, что не связано ни с чем, — либо лишнее, либо забыли вход.

### 4. Инварианты

Короткий список правил, которые нельзя нарушить. Проверенные на практике:

1. Из любого пуша ровно один шаг назад.
2. Одна сущность — один экран: тап по человеку в любом месте продукта ведёт в один и тот же профиль.
3. Все дороги к ключевому событию заканчиваются одним и тем же экраном-праздником и одной записью в данных.
4. Чего в продукте нет — того нет нигде (если переписки внутри продукта нет, её нет ни в одном узле, и все «написать» ведут наружу, в мессенджер).
5. **Мёртвых интерактивов не существует**: элемент без назначения в карте не рисуется.

## Порядок работы

1. Флоу и содержание экранов уже есть (FLOW.md) — ИА не заменяет их, а связывает.
2. Пишешь IA.md по схеме выше.
3. Мапишь на код: навигационный слой (стек + корни), затем экраны.
4. Прогоняешь каждый переход руками. Тап, который никуда не ведёт, — дефект архитектуры, а не «не успели».
5. Появилась новая фича — сначала строка в IA.md, потом код.

## Чек-лист перед сборкой экранов

- У каждого узла заполнены все четыре колонки?
- У каждого интерактива на экране есть строка «куда»?
- Условные переходы описаны с условием?
- Инварианты сформулированы и ни один экран их не нарушает?
- В графе нет узлов без входа и без выхода?
