# Product brief

## Контекст продукта
Программа «А» — повышение осведомлённости сотрудников в ИБ и устойчивости к атакам на основе социальной инженерии. Возможности: учебные фишинговые рассылки, анализ результатов, группировка и целевое обучение, библиотека шаблонов писем и веб-форм. Разделы: Пользователи, Атаки, Шаблоны, Обучение, Отчёты, Учащийся. → `sources/00-product-a-input.md`

**Текущая задача:** сводная аналитика (дашборд) на **отдельной странице** по обучению и атакам — не подмена раздела «Отчёты».

## Problem statement
Мы видим, что специалисты ИБ (соц. инженер, руководитель анализа) и зрители CISO/CTO/Директор ИБ сталкиваются с тем, что сводку по обучению и атакам собирают вручную из Excel/Word→PDF, потому что в платформе нет единого экрана «картины целиком». Это важно, потому что решения (доклад руководству, назначение курсов, оценка эффективности программы) опираются на разрозненные цифры и теряют время/связность. → `sources/interview-ib-specialists.md`

## Ключевые сценарии
1. **Доклад руководству:** ИБ собирает open/click/submit/report/(вложение|macro) + обучение → передаёт CISO/CTO (сейчас Excel/PDF).
2. **Назначить курсы:** по топу уязвимых (ФИО на сводке) / болевым точкам подразделений → действие из сводки.
3. **Оценить эффективность программы:** актуальный Risk Score / срез + факт обучения; единый индекс защищённости (запрос руководителя анализа). Без обязательной динамики 3–6–12 на первом экране (**решение**).
4. **Срез для SOC (v1):** уязвимые сотрудники + частые инциденты (отдельно от HR).
5. **Срез для HR (v1):** образование / обучение — отдельно от ИБ-дашборда.

## Текущий workflow (as-is)
| Шаг | Как сейчас | Источник |
|-----|------------|----------|
| Сбор цифр | Excel; Word с конвертацией в PDF | оба интервью |
| Инструмент вне «А» (пример) | EvilGo Phish + курсы; вручную «60% перешли» | руководитель анализа |
| Решение после цифр | Сообщить руководству; назначить курсы; оценить эффективность обучения | оба интервью |

## Обязательное на первом экране
Акцент: **последняя кампания / актуальный срез** — не окно 3–6–12 мес. (**решение**).

**Соц. инженер:** открыли / переходы / вложения / отправили данные / фидбэк; сколько проходит обучение; сколько не закончили; сколько завершили; динамика **последней** атаки.

**Руководитель анализа:** Risk Score; пользователи по уровню риска; число проведённых кампаний; дата последней кампании; метрики атак включая macro enabled; единый индекс.

**Топ уязвимых с ФИО** — на сводке (не только drill-down). (**решение**; constraint PII ниже)

**Подразделения:** сравнение по болевым точкам / типам атак **без** единого порога «плохо» / traffic-light. (**решение**)

## Явные «нет»
- Два режима «для ИБ» и «для руководства» **на одной странице** — оба респондента: нет.
- Динамика 3–6–12 на первом экране — **не нужна** (**решение**).
- Единое правило / порог «плохо» для подразделений — **нет** (**решение**).
- Связка «кликнул → назначили курс → завершил» сейчас не видна (руководитель анализа) — боль as-is, не отмена требования связки.

## Решения (зафиксированы человеком, 2026-09-15)
1. На первом экране достаточно последней кампании / актуального среза; динамика 3–6–12 **не** нужна.
2. Сравнение подразделений без жёсткого порога — болевые точки и типы атак, не traffic-light rule.
3. V1 аудитории: Primary ИБ + зрители CISO; **HR** — образование (обучение); **SOC** — уязвимые сотрудники и частые инциденты. Отдельные срезы/потребности, не dual-mode toggle.
4. ФИО топа уязвимых — **да, на сводке**.

## Технические / privacy constraints
- **PII:** ФИО сотрудников в топе уязвимых отображаются на сводном дашборде → учесть доступ по ролям, аудит просмотра и политику персональных данных при проектировании (не отменяет решение показывать ФИО).
- Интеграции/стек вне scope research.

## UI/UX ограничения
- Дашборд = отдельная страница; не проектировать UI в research.
- Не подменять дашборд разделом «Отчёты» (задача из input).
- Отдельные срезы HR / SOC — не два режима на одном экране; не dual-mode ИБ/руководство.
