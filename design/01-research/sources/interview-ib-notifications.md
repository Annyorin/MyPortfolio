# Интервью — ИБ / SOC · настройки уведомлений

**Кто брал:** владелец кейса (Аня).  
**Респондент:** SOC-специалист.  
**Роль:** совмещает аналитика 1, 2 и 3 линии + DFIR.  
**Контекст работы SOC:** по регламентам [NIST](https://www.nist.gov/).  
**Ключевое различение:** **alert ≠ инцидент** (алерт — сигнал; инцидент — подтверждённое событие по процессу).

## Скрининг (2 мин)

1. **Ваша роль: VM / SOC / руководитель ИБ / совмещаете?**  
   Совмещающий специалист: аналитик 1, 2 и 3 линии + DFIR.

2. **Кто в компании настраивает, кто только получает алерты?**  
   Настраивает уполномоченный человек; выше по статусу — админ (другие роли).

3. **Чем сейчас пользуетесь для алертов вне этой системы (почта, Telegram, KUMA, KSC, телефон)?**  
   VM-контур: из KUMA в Dragon — уведомление, что скан закончился.  
   В системе: уведомления для SOC и уведомления для организации заказчика.

## Контекст дежурства (8–10 мин)

4. **Последняя смена / неделя: что открывали, что свайпали?**  
   Совмещающий открывает **только уведомления о подтверждении инцидента**.  
   Руководству SOC все уведомления не нужны — быстрее дойдёт от аналитиков 1 / 2 / 3 линии.

5. **«Критично — разбудить» vs «можно утром в почте»? Кто решает?**  
   Будят аналитика 3 линии — аналитики 1 и 2 линии.

6. **Одно событие дважды (почта + мессенджер + SIEM)? Как относитесь?**  
   Нет (дублей в описанном контуре не бывает / не проблема).

7. **Telegram: личка, группа SOC, бот? Кто админ бота при увольнении?**  
   Не используем для всех уведомлений. Каждая роль может настроить лично под себя либо сделать общий чат.

## Процесс вне UI (3–5 мин)

19. **Кто ещё должен получать копию (руководитель, подмена на отпуск)?**  
    Подмена на время отпуска.

20. **Что происходит после алерта: открыть консоль, закрыть инцидент, эскалировать ИТ?**  
    Закрыть инцидент; зависит от правил из nist.gov.  
    *(Уточнение исследования: речь о работе с **инцидентом** после подтверждения; alert сам по себе ≠ инцидент.)*

    Шум уведомлений приводит к пропуску критичного — после этого могут «надавать по шапке» от начальства.

## Мини-вывод

SOC в этом контуре — линии 1→2→3 + DFIR по NIST; до руководства доводят люди, а не поток всех алертов. На экране важны **подтверждение инцидента** и гибкая персональная/ролевая политика, а не «включить всё». Шум опаснее пустого канала: из-за него пропускают critical. Alert и инцидент в копирайте и модели не смешивать. Настройка — разовый акт уполномоченным/админом; Telegram — опция роли или общий чат, не общий ор на всё.
