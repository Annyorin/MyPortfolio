## Вопрос и границы

Кто аудитория all-in-one консоли ИБ и как на рынке устроены оповещения, если каналы — система, почта и Telegram.

В границах: роли, работа настройки уведомлений, конкуренты РФ и зарубежные, текущий флоу (владелец), эвристический разбор UI после первой итерации, UX-референсы Monday/Weeek, сценарии из Figma.

Вне: весь продукт, визуал/бренд, код, цены.

Метод: кабинет + competitive; паттерны Weeek и Monday; прогон n=10 (first-click, мысли вслух, запись экрана); разбор UI 2026-09-28; сценарии Figma; **1 интервью SOC** (совмещающий L1–L3+DFIR, регламент NIST) — `01-research/sources/interview-ib-notifications.md`. Задача прогона: «подключить активы в Telegram — как и куда вы пойдёте?». Секунды с записи — дыра.

## Продукт

Система управления безопасностью для организаций: сети и активы.

Делает: сканирует активы на уязвимости; ранжирует уязвимости и инциденты; инвентаризация активов; состояние агентов EDR.

Заявлено владельцем: интеграции Kaspersky (KATA, KUMA, CyberTrace) и AbuseIPDB; база CVE; роли; файловое хранилище; Excel/PDF/CSV; карта филиалов России; Telegram и почта; методички; топология сети; автоскан; статистика уязвимостей, портов и технологий.

Публично (Иннополис, 26.11.2024): многоступенчатый анализ связанных рисков; сканы портов, веб-приложений и сайтов; человеческий фактор (пароли в файлах); карта топологии; группировка активов и ответственные. У отдельных компонентов есть конкуренты, ставка — объединение направлений.

Задача кейса: экран и флоу настроек уведомлений. Не весь продукт.

## Эволюция флоу

### Было (ввод владельца, 2026-09-16)

Одно модальное окно. Вкладки — каналы: системные, почта, Telegram. На каждой вкладке одинаковое дерево. Группы: уязвимости, активы, технологии, инциденты. Нет чекбокса на группу. Тройной проклик. Цена: время; ошибки — забыть сохранить и забыть, что включил на прошлой вкладке.

### Стало после первой итерации (разбор UI, 2026-09-28)

Архитектура в целом верная: 3 вкладки → мастер-чекбокс «Выбрать все» → 6 групп → счётчики «X из N» → «Применить ко всем каналам» внизу.

Остались проблемы структуры и копирайта (не «нет мастера», а доводка):

1. **Две колонки групп** — нет горизонтальной связи; глаз не знает, читать построчно или по колонкам. Группа «Получать уведомления о» в правой колонке выбивается (глагол, не сущность).
2. **Слабое имя группы** — остальные существительные (Уязвимость, Актив, Заявка); «Получать уведомления о» — незаконченный оборот → переименовать в «Сканирование» / «Процессы».
3. **«Создан отчёт об инцидентах»** — одиночный пункт на уровне групп → внутрь «Инцидент» или явный standalone.
4. **«Применить ко всем каналам»** сливается с Отмена/Сохранить → разнести зоны (синхронизация ≠ сохранение).
5. **Мастер без суммарного счётчика** — у групп «3 из 8», у мастера нет → «Выбрать все · 10 из 26».
6. **Вкладки без состояния канала** — Telegram с 0 или без подключения выглядит как Почта → индикатор / счётчик / серый.

Приоритет правок: переименовать группу и убрать orphan-пункт (быстро) → счётчик мастера, разнос кнопок, индикатор вкладок → одна колонка (лейаут).

### Target (wireframes + IA)

Одна колонка групп; вкладки с счётчиком и warning; мастер с суммой; Apply all отдельно от Save; Connect Telegram/SMTP отдельно от галочек. Каркасы: `design/04-prototype/wireframes/innodragon-notifications-wireframes.html`. Доска FigJam: UF-Portfolio (User Flow, IA, Benchmarks).

## Аудитория

Основной экран настроек: специалист VM; SOC (в т.ч. совмещающий L1–L3 + DFIR); уполномоченный / админ консоли. Политика «какие события куда» — чаще **разовая** настройка, гибкая, не «вкл всё».

Зрители сигнала: руководство SOC / CISO — им не нужен поток всех алертов; быстрее эскалация от аналитиков 1–3 линии.

В контуре системы также: уведомления организации заказчика. VM: сигнал «скан закончился» (KUMA → Dragon).

Не аудитория этого экрана: сам сканер, агент EDR, методические материалы.

**Модель (интервью):** alert ≠ инцидент. Процесс закрытия — по NIST.  
**Каналы (интервью):** Telegram не для всех уведомлений — лично под роль или общий чат. Универсальное «Critical сразу в Telegram» не подтверждаем.

## Процесс SOC и NIST CSF 2.0

Источник: интервью SOC (L1–L3+DFIR) + [NIST CSF 2.0](https://www.nist.gov/cyberframework) / [SP 800-61r3](https://csrc.nist.gov/pubs/sp/800/61/r3/final) как Community Profile для IR.

| Функция CSF | Что делает SOC в контуре | Связь с уведомлениями Dragon |
|-------------|--------------------------|------------------------------|
| **Govern / Identify / Protect** | Регламент, роли, подготовка к смене | Политику оповещений собирает уполномоченный / админ **один раз** |
| **Detect** | Алерт из KUMA, скана, консоли | VM: KUMA → Dragon «скан закончился». Алерт ≠ инцидент |
| **Respond** | L1/L2 triage и подтверждение; будят L3; DFIR | Совмещающий открывает в основном **подтверждение инцидента**. Эскалация людьми, не потоком «всех» |
| **Recover** | Восстановление, связь с заказчиком | В системе — уведомления SOC и организации заказчика |

Страх: шум → пропуск critical → санкции руководства. «Вкл всё» почти не используют. Руководству SOC быстрее от линий 1–3, чем из полной ленты.

## Job stories (из разбора UI + сценариев Figma)

Формат: Когда… хочу… чтобы…

| ID | Job | Источник |
|----|-----|----------|
| J1 | Когда захожу в настройки, хочу сразу понять, что уже включено по каналам, чтобы решить, менять ли | Figma сц. 1 |
| J2 | Когда собираю политику, хочу одну колонку групп сверху вниз, чтобы не гадать про чтение | UI #1 |
| J3 | Когда ищу группу, хочу имена-сущности, чтобы не спотыкаться о глагол | UI #2 |
| J4 | Когда настраиваю инциденты, хочу «отчёт» внутри группы, чтобы понимать иерархию | UI #3 |
| J5 | Когда настроил один канал, хочу отдельно «применить ко всем», чтобы не путать с Save | UI #4 |
| J6 | Когда включаю пункты, хочу «X из N» и на мастере, чтобы видеть общую долю | UI #5 |
| J7 | Когда смотрю вкладки, хочу видеть подключён ли канал и сколько включено | UI #6, сц. 3 |
| J8 | Когда случайно снял группу заголовком, хочу Undo, чтобы не собирать руками | Figma сц. 2 |
| J9 | Когда Telegram не подключён, хочу предупреждение до save | Figma сц. 3 |
| J10 | Когда долго настраивал, хочу не потерять правки из‑за Отмена рядом с Save | Figma сц. 4 |
| J11 | Когда вижу минус на группе, хочу однозначную логику вкл/выкл | Figma сц. 5 |

**Main job:** понять состояние каналов/событий и безопасно сохранить политику за один заход (J1 + J7).

**Non-jobs:** само сканирование; закрытие инцидента; карта России; конструктор произвольных правил Qualys; онбординг бота как отдельный продукт (только индикация и блок до Connect).

## Боли

### Базовые (владелец + рынок)

Дерево событий копировалось на каждый канал. Не было мастер-чекбокса группы. Сохранение и состояние вкладки легко потерять. На рынке канал чаще действие правила, не вкладка с копией каталога.

### После первой итерации (разбор UI + Figma)

Когнитивная нагрузка двух колонок. Слабый нейминг группы. Orphan-пункт отчёта. Apply all потерян у футера. Нет суммарного счётчика. Нет сигнала «канал не подключён». Нет Undo после массового выкл. Путаница indeterminate (минус). Риск потери правок (Отмена ≈ Save визуально). Ложная уверенность: галочки на неподключённом Telegram.

## Сценарии (Figma, реализованные в проекте)

Источник: [Портфолио → Сценарии](https://www.figma.com/design/xboMnqU5JURL0xlzxN7edN/?node-id=481-15308).

**Сц. 1 — заход в настройки:** открыть → смотреть типы и каналы → оценить → сохранить при изменениях → назад в «Уведомления».

Состояния (мин. 6): пусто; частично (минус); заполнено; недоступно (серые чекбоксы, канал не подключён); ошибка сети; сохранение / автосохранение + уведомление.

**Сц. 2 — случайно выкл группу:** нет confirm при клике по заголовку; нет Undo → toast «Отменить» 5 с или подсветка строк.

**Сц. 3 — канал не подключён:** включил Telegram, сохранил, алертов нет → warning на вкладке / в заголовке колонки + тултип «не подключён».

**Сц. 4 — потеря правок:** Отмена рядом с Save → автосохранение или защита от случайного закрытия.

**Сц. 5 — минус вводит в заблуждение:** минус → только «вкл всё»; выкл из галочки; тултип «Нажмите чтобы выбрать всё».

Corner cases: нет бота Telegram; возврат после ошибки сети; вернуть исходные до сброса; закрепить заголовок при скролле.

## UX-референсы проектирования (не ИБ)

На них опирались при раскладке экрана (доска FigJam «Benchmarks»).

**Monday.com** — Profile → Notifications: таблица типов событий × колонки каналов (Bell / Email / Mobile). Slack подключается отдельно, не копирует дерево. Mute — на уровне доски, не вторая копия каталога.  
Взять: событие отдельно от канала.  
Ссылки: [Notifications explained](https://support.monday.com/hc/en-us/articles/360001292545-Notifications-explained), [Email](https://support.monday.com/hc/en-us/articles/115005319529-Email-notifications), [Slack](https://support.monday.com/hc/en-us/articles/360002363999-Slack-integration).

**Weeek.net** — сверху каналы (центр, push, мессенджеры, in-app, mobile, почта); «Подключить» Telegram/VK/Slack отдельно; снизу типы событий с переключателями; на событии — иконки форматов. В хелпе скриншоты (Изобр. 1–11).  
Взять: Telegram рядом с почтой; Connect отдельно; ближе к Dragon, чем Monday.  
Ссылки: [настройка](https://weeek.net/ru/help/workspace/uvedomlenia/nastrojka-uvedomlenij-1), [виды](https://weeek.net/ru/help/workspace/uvedomlenia/vidy-uvedomlenij-1), [центр](https://weeek.net/ru/help/workspace/uvedomlenia/centr-uvedomlenij-1).

Вывод: оба рефа подтверждают «канал ≠ вкладка с копией дерева» и отдельный Connect. Антипаттерн KSC — против обоих.

## Что не копировать

Вкладки метода доставки как в Kaspersky Security Center.

Конструктор Qualys как единственный UI для четырёх закрытых групп.

Кнопку «скопировать с соседней вкладки» как замену матрице.

Slack вместо Telegram для российского дежурства.

Двухколоночную раскладку групп без горизонтальной логики.

Глагольные имена групп и orphan-пункты на уровне групп.

## Решения для кейса

### Уже принято (первая итерация → прод)

Мастер-чекбокс; счётчики на группах; «Применить ко всем каналам»; вкладки каналов сохранены как IA продукта; макет в прод; команда 4 фронта + 4 бэка + дизайнер.

### Следующий слой (из разбора 2026-09-28)

Одна колонка групп. Переименовать «Получать уведомления о» → «Сканирование». Отчёт — в группу «Инцидент». Суммарный счётчик на мастере. Индикатор/счётчик на вкладках. Разнести Apply all и Save. Логика минуса + Undo toast. Connect Telegram отдельно с явным warning.

Изначально в research (2026-09-16) цель формулировали как «каналы колонками, не вкладками». В проде остались вкладки + мастер/apply — это допустимый компромисс, если вкладка показывает состояние и не требует тройного проклика без группового чекбокса. Колонки Monday — эталон для следующей крупной перестройки IA; текущий слой чинит discoverability и ошибки внутри вкладок.

Конструктор правил не берём.

## Гипотезы (Lean UX)

| ID | Тип | Гипотеза | Сигнал |
|----|-----|----------|--------|
| H1 | problem | Две колонки увеличивают время ориентации и ошибочные клики | First-click / time-to-first-action |
| H2 | solution | Одна колонка + имя «Сканирование» снизит спотыкания на ярлыке | Think-aloud: «найди завершение скана» |
| H3 | solution | Счётчик на мастере ускорит решение «менять / не менять» | Сц. 1, время до решения |
| H4 | solution | Индикатор на вкладке + warning уберёт ложную уверенность после save | Сц. 3, доля ожидающих алерты в TG |
| H5 | solution | Разнос Apply all и Save снизит путаницу действий | First-click: «скопировать» vs «сохранить» |
| H6 | solution | Toast Undo 5 с снизит необратимые массовые выключения | Сц. 2 |
| H7 | solution | Защита от случайной Отмены / автосейв снизит потерю длинных сессий | Сц. 4 |
| H8 | solution | Минус → только «вкл всё» + тултип снизит путаницу | Сц. 5, лишние клики |

Топ-3 к проверке: **H4**, **H6**, **H3**.

## Прогон с людьми (владелец, 2026-09-16)

Команда как у InnoPhish: 4 фронта, 4 бэка + дизайнер.

Макет ушёл в прод.

Исследование: поиск паттернов у конкурентов, доска Weeek; позже — Monday как матрица канал×событие.

Прогон: десять человек. Владелец назвал A/B. Протокол: тест первого клика, мысли вслух, **запись экрана**. Задача: подключить активы в Telegram — как и куда вы пойдёте?

На записи можно выбрать среднее время закрытия действия и пользовательский путь. Файл в репозитории не лежит. Секунды и куда вели клики в кейс не ставить, пока нет цифры или видео.

Сплита трафика не было. После прода в бою время не переснимали.
