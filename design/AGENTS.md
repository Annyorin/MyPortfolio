# Метасреда продуктового дизайна

Эта папка вложена в пайплайн `rdudov/agents`. Из корня репозитория пути сред —
`design/01-research/` … `design/05-code/`. Скиллы лежат в корневом `.cursor/skills/`.
Координатор дизайн-слоя — субагент `designer` (`11_designer_prompt.md`).
Утверждённое ТЗ пайплайна главнее UX-PRD: исследование дополняет, а не заменяет ТЗ.

Это корень метасреды. Сам корень **не выполняет предметную работу** — он маршрутизирует
задачу в одну подсреду и следит за соблюдением границ между ними.

## Для кого

Метасреда и проекты внутри неё рассчитаны на **продуктового UX/UI-дизайнера**
с опытом около **10 лет**: человека, который сам ведёт исследование, структуру,
визуал, прототип и связку с кодом — часто без отдельной команды разработки.

От агента ожидается язык и уровень решений дизайнера, а не разработчика «с нуля»:
- объяснять trade-off простым языком, без лишнего жаргона;
- не упрощать до уровня новичка — термины вроде JTBD, PRD, дизайн-система, токены
  допустимы, если они общеприняты в продуктовом дизайне;
- предлагать варианты с обоснованием для пользователя и бизнеса, а не только «как
  сверстать».

Среда 5 (Code) существует как зеркало дизайн-системы, а не как замена дизайнеру:
дизайнер задаёт направление, агент помогает собрать и синхронизировать.

## Подсреды

| # | Среда | Путь | Отвечает за | Изоляция |
|---|-------|------|-------------|----------|
| 1 | Research | `01-research/` | брифы, конкуренты, инсайты, гипотезы | мягкая |
| 2 | Design System | `02-design-system/` | Figma-синк, foundations, компоненты, менеджмент Figma | **строгая** |
| 3 | Content | `03-content/` | тексты, изображения, контент-стратегия на базе Research | мягкая |

Подробности маршрутизации — в [`_shared/registry.md`](_shared/registry.md).

## Правило маршрутизации

1. Определи целевую среду по таблице выше. При неоднозначности — спроси пользователя,
   не «размазывай» задачу по нескольким средам.
2. Перейди в её каталог, прочитай её `AGENTS.md` и работай **только внутри него**.
3. Всё, что нужно от других сред, бери из их `outputs/` — это единственная публичная
   поверхность среды. Внутренности чужой среды не читаются и не редактируются.
4. Если задача действительно требует изменений в двух средах — разбей её на две задачи
   и выполни последовательно, оформив передачу через контракт
   (см. [`_shared/contracts/README.md`](_shared/contracts/README.md)).

## Строгая изоляция среды 2

`02-design-system/` — самая объёмная среда. Задача, адресованная ей, выполняется
**целиком внутри неё**: ни один шаг не выносится в корень или в другие среды.
Из неё наружу уходит только манифест `02-design-system/outputs/ds-manifest.md`.
Остальные среды читают этот манифест и никогда — внутренние файлы среды 2.

Для работы с большим объёмом контекста среды 2 запускай отдельный субагент
(`Task`) с чистым контекстом, ограниченный каталогом `02-design-system/`, и требуй
от него сжатую сводку, а не сырой дамп.

## Figma

Подключение — официальный remote MCP-сервер Figma (`https://mcp.figma.com/mcp`) по OAuth,
с чтением и записью. Протокол целиком описан в `infra/subskills/figma-mcp`: проверка
сессии, OAuth при первом вызове, разбор ссылок, последовательности чтения и записи,
экономия лимита.

Ссылка `figma.com` в запросе — сигнал загрузить этот скилл до любых других действий.
Файл опознаётся по `fileKey` через [`02-design-system/figma/registry.md`](02-design-system/figma/registry.md),
и задача уходит в среду-владельца этого файла.

## Поток данных

```
Research ──digest + prd──> Content ──copy/visual──> Prototype
                  │                                       ▲
                  └──────────jtbd/сценарии────────────────┘
Design System ──ds-manifest──> Prototype (зеркало в Figma)
Design System ──ds-manifest──> Code      (зеркало в коде)
Design System <──запрос компонента── Prototype, Code (через контракт)
```

Дизайн-система отражается дважды: в Figma через среду 4 и в коде через среду 5.
Оба зеркала read-only и сверяются с `version` манифеста перед работой.

## Инварианты Figma ↔ код

Шесть правил, которые нельзя нарушать при работе с двумя зеркалами дизайн-системы.
Полная версия со ссылками на источники — [`_shared/figma-code-invariants.md`](_shared/figma-code-invariants.md).

1. **Только токены** — цвета, размеры, шрифты не захардкожены в компонентах; источник — `05-code/tokens/`.
2. **Имена один в один** — компонент в Figma и React называется одинаково; вариант = проп.
3. **Синхронизация сразу** — каждая итерация зеркалируется в реестр и манифест, долг не копится.
4. **Сверка паритета** — после значимого изменения проверять соответствие Figma и кода (скилл `design-system-sync`, фаза дрифта).
5. **Запись в Figma** — не `resize(W, 0)` на auto-layout; TEXT только с текстовым стилем (скилл `figma-mcp`).
6. **MCP** — после настройки `.cursor/mcp.json` перезапустить IDE (скилл `figma-mcp`).

## Скиллы

Процедуры лежат в `.cursor/skills/` шестью группами-мультискиллами и грузятся только
по вызову. Триггерятся роутеры групп, подскилл роутер читает как файл. Выбор группы —
по [`_shared/skills-map.md`](_shared/skills-map.md); тела скиллов пачками не читать.

Обзор для человека — [`infoSkills.md`](infoSkills.md). При добавлении или правке скилла
обновляй его вместе с `skills-map.md`.

## Общие принципы

- **Контекст — конечный ресурс.** Не подгружай файлы «на всякий случай»; ищи по
  структуре каталогов и читай точечно (just-in-time).
- **Заметки вместо памяти.** Прогресс длинных задач пиши в `NOTES.md` своей среды.
- **Один артефакт — один файл.** Каждый файл имеет frontmatter (`type`, `status`, `updated`).
- **Никакой работы без владельца.** Если у артефакта нет среды-владельца — он не создаётся.
